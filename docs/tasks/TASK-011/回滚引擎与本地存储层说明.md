- 任务：QUOT-13 / T11

## 1. 范围与结论

本任务交付两件事：

1. **一键回滚**（`src/core/rollback/`）：把已迁移项反向还原——拆 junction、把目标数据回拷到源同盘的恢复槽、校验、同卷原子换位、恢复配置备份、删除本 job 的目标副本、写入历史与规则学习。
2. **本地持久化层**（`src/core/store/`）：数据根布局、原子 JSON 写入、引导指针、设置、迁移/回滚历史、规则学习、迁移与回滚 journal、JSONL 日志。

结论：

- 回滚严格按架构 §6.7 的顺序执行：**只有校验通过才把恢复副本换位为源**；目标副本只在源已还原、配置已恢复后才删除；任何失败至少保留一份完整数据。
- 预检阶段不写任何文件：目标盘不可用、junction 指向别处、非本 job 链接、工具运行中、空间不足、迁移 journal 缺失等情况一律在第一次变更前返回。
- 中断恢复 `recover_rollback()` 以"观察优先、journal 消歧"为原则；证据不足时进入 `ROLLBACK_RECOVERY_REQUIRED` 并停止，不猜测、不删除。
- 所有持久化文件（设置、历史、规则、journal）都走同一原语：同目录 `.tmp-<pid>` → flush + `fsync` → `os.replace`；断电最多留下临时文件，不会产生半个 JSON。
- 损坏文件统一隔离为 `*.corrupt-<stamp>`，读取方不抛异常，返回默认值并附 warning。
- 存储路径与 `docs/功能需求.md` §4.2 完全一致；数据根切换在 `data/` 非空时被拒绝（§4.5）。
- 新增 56 个回滚测试与 121 个存储测试；全套 **437 个测试全部通过**（T10 基线 260）。

本任务**不包含**：UI 与 app 层编排、系统托盘、真实用户数据回滚演练、平台层剩余空间原语、macOS 完整适配（决策 0004 归 T21）。

- `job8` 一律取 job_id 的前 8 位小写十六进制；journal 文件名使用完整 job_id。

- 回滚只处理"源是 junction 且指向记录目标"这一种正常起点；其它形态进入状态异常或恢复流程。

## 5. 一键回滚流程

### 5.1 预检（S1）

`precheck_rollback()` 只读，返回四种模式之一：

| 模式 | 条件 | 说明 |
|---|---|---|
| `rollback` | 源是 junction、指向记录目标；目标存在且带本 job 所有权标记 | 可执行 |
| `already_rolled_back` | 源是普通目录；记录目标不存在 | 直接成功返回 |
| `residual_copy` | 源是普通目录；目标仍存在且带本 job 标记 | 需 `confirm_residual_delete=True` 才删除残留副本 |
| `blocked` | 其余情况 | 返回错误码，不触碰任何路径 |

预检顺序：

1. 校验 `RollbackRequest`：job_id 8–32 位十六进制、tool_id、源与目标非空且不同路径。
2. 若提供 `jobs_dir`，加载迁移 journal，比对 tool/source/final；journal 缺失 → `RECOVERY_REQUIRED`。journal 状态不是 `DONE`/`LINKED_CLEANUP_PENDING` 只记 warning。
3. 判定源类型（missing/junction/link/dir/file/other）与目标状态（存在、是否本 job 所有、字节数、文件数）。
4. junction 场景：目标缺失 → `TARGET_UNAVAILABLE`；无标记 → `STATE_ABNORMAL`；链接指向别处 → `STATE_ABNORMAL`。
5. 进程复查：工具运行中或进程枚举失败（unknown）→ `PROCESS_BUSY`。
6. 空间检查：所需空间 = `expected_bytes`（未给则采样目标大小）；不足 → `INSUFFICIENT_SPACE`。provider 不可用时只记 warning，不误判。

### 5.2 拆链（S2）

- `link.remove_own_link()` 只接受"存在、是 junction、指向记录目标"的源；其它形态抛 `LinkStepError`，什么都不删。
- 拆链失败 → `STATE_ABNORMAL` / `LINK_REMOVE_FAILED`，junction 保持原样。
- 拆链后若源路径仍被占用 → `ROLLBACK_RECOVERY_REQUIRED`，不猜测。
- 拆链成功后 journal 记 `ROLLBACK_LINK_REMOVED`。

### 5.3 回拷（S3）

- 清理上一次中断留下的本 job 恢复槽（名称必须是 `.dw-restore-<job8>`），删除失败 → `RECOVERY_REQUIRED`。
- 创建恢复槽，用 `copy_to_staging()` 把目标复制到 `恢复槽/<basename>`，带 `expected_bytes` / `expected_files` 与取消令牌。
- 传输可注入（`transfer=`），默认 robocopy；`CopyResult.exit_code >= 8` 视为失败。
- 取消、I/O 错误、退出码异常 → 失败处理：删除恢复槽、尝试重建 junction、状态 `ROLLBACK_FAILED`（重建失败则 `ROLLBACK_RECOVERY_REQUIRED`）。
- 成功后 journal 记 `ROLLBACK_COPIED`。

### 5.4 校验（S4）

- `verify_trees()` 逐文件比较数量、字节数与 SHA-256。
- 校验失败 → **保留目标完整副本**、删除未通过的恢复槽、重建 junction，状态 `ROLLBACK_FAILED` / `ROLLBACK_VERIFY_FAILED`。
- 校验通过后移除恢复副本里的 `.dw-owner-<job8>.json`，避免把迁移所有权标记带回源目录；移除失败按 `SOURCE_RESTORE_FAILED` 处理。
- journal 记 `ROLLBACK_VERIFIED`。

### 5.5 换位（S5）

- 换位前再次确认源路径未被重建、恢复副本与源同卷。
- `ops.rename(恢复槽/<basename>, 源路径)` 同卷原子改名。
- 成功即 `source_restored=True`；journal 记 `ROLLBACK_SOURCE_READY`，并探测源目录可读性（不可读只记 warning）。

### 5.6 配置恢复（S6，AC-ROL-06）

`restore_configs(backup_dir, choice, expected_tool_id, expected_job_id)` 读取迁移 manifest，逐文件处理：

| 场景 | 条件 | 默认动作 | 结果状态 |
|---|---|---|---|
| A | 当前文件与备份内容一致 | 不重写 | `identical` |
| B | 当前文件缺失 | 从备份恢复 | `restored_missing` |
| C | 当前文件被用户修改 | 保留用户版本（`keep`） | `kept_user` |
| C' | 用户明确选择 `restore` | 覆盖为用户要求 | `restored_user_choice` |
| D | 备份目录/manifest/文件缺失或损坏 | 报告不可用，不改当前文件 | `unavailable` / `backup_missing` / `backup_corrupt` |

- manifest 必须匹配 `tool_id` 与 `job_id`，`source_root` 必须存在且目标路径落在其内；`..`、绝对路径、盘符、空组件一律拒绝，再访问文件系统。
- 每个文件重新计算备份摘要，避免 manifest 被篡改或截断。
- 写入使用 `atomic_write_bytes`；写失败保留原路径内容，记为 `restore_failed`。
- 聚合状态：全部成功 → `restored`/`kept`；部分成功 → `partial`；全部失败/不可用 → `failed`；无条目 → `not_required`。
- **配置恢复失败不改变数据结论**：源已还原、目标仍在，只追加 warning，journal 仍记 `ROLLBACK_CONFIG_RESTORED`（payload 带完整配置结果）。

### 5.7 清理（S7）

- `cleanup.remove_owned_tree(final_path, 父目录, job_id)` 要求：父目录匹配、目录名不受 `.dw-*` 限制、目录内存在本 job 所有权标记、根与子项不跟随 reparse point。
- 删除失败 → 状态仍为 `ROLLED_BACK`，置 `residual_copy=True`、`error_code=TARGET_DELETE_FAILED`，源与目标都保留，由人工或后续清理处理。
- 成功 → `target_removed=True`。
- 最后清理恢复槽（job 作用域），失败只记 warning。

### 5.8 记录（S8）

- 历史：`HistoryStore.record_rollback(...)`，`result=rolled_back`，`job_id`、`size`、`stage=record`。
- 规则学习：`LearnedRulesStore.mark_red(item_id, reason="rolled_back", rule_id="rollback")`。
- journal：`ROLLED_BACK`，payload 含 `target_removed`、`residual_copy`、配置结果。
- 历史/规则写入失败只记 warning，不影响回滚结论（它们是诊断与学习数据，不是事实源）。

## 6. 失败与回滚矩阵

| 情况 | 结果状态 | 错误码 | 源 | 恢复槽 | 目标 | 链接 |
|---|---|---|---|---|---|---|
| 请求非法 | `ROLLBACK_FAILED` | `INVALID_ROLLBACK_INPUT` | 不变 | 未创建 | 不触碰 | 不变 |
| 迁移 journal 缺失/不匹配 | `ROLLBACK_FAILED` | `RECOVERY_REQUIRED` / `INVALID_ROLLBACK_INPUT` | 不变 | 未创建 | 不触碰 | 不变 |
| 工具运行中 / 进程未知 | `ROLLBACK_FAILED` | `PROCESS_BUSY` | 不变 | 未创建 | 不触碰 | 不变 |
| 空间不足 | `ROLLBACK_FAILED` | `INSUFFICIENT_SPACE` | 不变 | 未创建 | 不触碰 | 不变 |
| 目标盘不可用 | `STATE_ABNORMAL` | `TARGET_UNAVAILABLE` | 不变 | 未创建 | 不存在 | 保留 |
| junction 指向别处 | `STATE_ABNORMAL` | `STATE_ABNORMAL` | 不变 | 未创建 | 不触碰 | 保留 |
| 目标无本 job 标记 | `STATE_ABNORMAL` | `STATE_ABNORMAL` | 不变 | 未创建 | 不触碰 | 保留 |
| 源是非 junction 链接 / 文件 | `STATE_ABNORMAL` | `STATE_ABNORMAL` | 不变 | 未创建 | 不触碰 | 保留 |
| 源与目标都缺失 | `STATE_ABNORMAL` | `STATE_ABNORMAL` | — | 未创建 | — | — |
| 源缺失、目标在且为本 job 所有 | `ROLLBACK_FAILED` | `RECOVERY_REQUIRED` | 缺失 | 未创建 | 保留 | 无 |
| 已回滚（源普通目录、目标无） | `ALREADY_ROLLED_BACK` | — | 不变 | — | — | — |
| 残留副本未确认 | `RESIDUAL_COPY`（blocked） | — | 不变 | — | 保留 | — |
| 残留副本已确认、删除成功 | `RESIDUAL_COPY` | — | 不变 | — | 删除 | — |
| 拆链失败 | `STATE_ABNORMAL` | `LINK_REMOVE_FAILED` | 不变 | 未创建 | 不触碰 | 保留 |
| 拆链后源路径被占用 | `ROLLBACK_RECOVERY_REQUIRED` | `STATE_ABNORMAL` | 被占用 | 未创建 | 保留 | 已拆 |
| 变更前取消 | `ROLLBACK_FAILED` | `CANCELLED` | 不变 | 未创建 | 不触碰 | 保留 |
| 回拷取消 / 失败 | `ROLLBACK_FAILED` | `CANCELLED` / `ROLLBACK_COPY_FAILED` | 不变 | 删除 | **保留** | 重建 |
| 校验失败 | `ROLLBACK_FAILED` | `ROLLBACK_VERIFY_FAILED` | 不变 | 删除 | **保留** | 重建 |
| 换位失败（源被重建/跨卷/改名失败） | `ROLLBACK_FAILED` | `SOURCE_RESTORE_FAILED` | 不变或缺失 | 删除 | **保留** | 不重建 |
| 任一失败后 junction 重建失败 | `ROLLBACK_RECOVERY_REQUIRED` | `RECOVERY_REQUIRED` | 保持现状 | 视阶段 | 保留 | 无 |
| 配置恢复失败/部分 | `ROLLED_BACK` + warning | 配置结果内记录 | 已还原 | 已清 | 删除 | — |
| 目标删除失败 | `ROLLED_BACK` | `TARGET_DELETE_FAILED` | 已还原 | 已清 | 保留（残留副本） | — |

要点：

- 拆链之后的所有失败路径都先尝试重建 junction，保证"源路径仍可用"；重建失败才升级为 `ROLLBACK_RECOVERY_REQUIRED`。
- 校验失败**保留目标完整副本**（与 T10 的 S8 策略一致）：多一份完整数据只会更安全。
- 配置失败不改变 `data_kept`；数据结论与配置结论分离。

## 7. 中断恢复（`recover_rollback`）

输入：job_id、tool_id、源与目标路径、可选 `restore_dir`、`recorded_state`、`jobs_dir`、历史/规则路径、注入的 `ops`。

流程：

1. 若给 `jobs_dir`，加载 `<job_id>-rollback.json`；journal 缺失且没有 `recorded_state` → `RECOVERY_REQUIRED`；tool/source/final 不匹配 → `RECOVERY_REQUIRED`。journal 的 `restore_dir` 默认作为恢复槽，必须通过"父目录 = 源父目录 + 名称匹配 `.dw-restore-<job8>`"校验。
2. `recorded_state` 已属终态 → 直接返回，无副作用。
3. 观察源/目标/恢复槽：源类型、链接目标是否匹配、目标是否本 job 所有、恢复槽与其中子目录类型。
4. 按下列矩阵分派；所有删除都限定在 journal 记录的路径与本 job 命名内。

| 观察到的状态 | recorded_state | 动作 | 结果 |
|---|---|---|---|
| 源=普通目录，目标无 | 回滚前状态 | 清恢复槽 | `ROLLED_BACK` |
| 源=普通目录，目标=本 job 目录 | `ROLLBACK_PLANNED` 等未还原状态 | 清恢复槽 | `ROLLBACK_RECOVERY_REQUIRED`（记录与事实矛盾） |
| 源=普通目录，目标=本 job 目录 | `ROLLBACK_VERIFIED` / `SOURCE_READY` / `CONFIG_RESTORED` | 删目标、恢复配置、清槽、记录 | `ROLLED_BACK` |
| 源=普通目录，目标=非目录或无标记 | 任意 | 不删 | `ROLLBACK_RECOVERY_REQUIRED` |
| 源=匹配 junction，目标=本 job 目录 | 任意 | 保留链接 | `ROLLBACK_FAILED`（`link_removed=False`） |
| 源=非 junction 链接 / 文件 | 任意 | 不删 | `ROLLBACK_RECOVERY_REQUIRED` |
| 源缺失，恢复槽子目录存在，state=`ROLLBACK_VERIFIED` | — | 同卷换位、配置、删目标、清槽 | `ROLLED_BACK` |
| 源缺失，恢复副本未校验 | 未校验状态 | 不换位；尝试重建链接 | `ROLLBACK_FAILED`（`relinked=True`） |
| 源缺失，目标在、恢复副本可换位 | `ROLLBACK_VERIFIED` | 换位后完成清理 | `ROLLED_BACK` |
| 源缺失，目标在、无可换位副本 | 任意 | 重建链接、清 job 恢复槽 | `ROLLBACK_FAILED` / `RECOVERY_REQUIRED` |
| 源缺失，目标缺失、无恢复副本 | 任意 | 不删 | `ROLLBACK_RECOVERY_REQUIRED` |
| 恢复槽是文件 / 名称或父目录不符 | 任意 | 不删 | `ROLLBACK_RECOVERY_REQUIRED` |
| 无回滚 journal 且无 recorded_state | — | 不删 | `ROLLBACK_RECOVERY_REQUIRED` |

- 恢复会更新 journal（`mark_recovered`）并写历史/规则；journal 更新失败只记 warning。
- 重复执行：终态直接返回；非终态在收敛后第二次观察即命中已完成条件，状态与数据不变。

## 8. 幂等性

| 操作 | 重复执行行为 |
|---|---|
| `precheck_rollback` | 纯观察，无副作用 |
| `rollback` | 已回滚 → `ALREADY_ROLLED_BACK`；残留副本 → 需再次确认 |
| `remove_own_link` | 链接不存在 → 无操作；指向别处 → 拒绝 |
| `remove_owned_tree` | 路径不存在 → 空错误列表 |
| `restore_configs` | 内容一致 → `identical`，不重写 |
| `recover_rollback` | 终态直接返回；非终态收敛后重跑状态不变 |
| `HistoryStore` / `LearnedRulesStore` | 重复写产生追加记录/幂等更新，不破坏文件 |
| `JsonlLogger.rotate` | 重复执行删除同一集合，无副作用 |

## 9. 进度事件

`progress_cb` 收到统一结构：

```json
{"stage": "precheck|link_remove|copy|verify|restore|config|cleanup|record|recover",
 "status": "start|progress|done|failed",
 "job_id": "...", "tool_id": "...", "elapsed_seconds": 0.12, "...": "阶段字段"}
```

成功路径固定顺序：

```
precheck:start → precheck:done
→ link_remove:start → link_remove:done
→ copy:start → copy:progress* → copy:done
→ verify:start → verify:done
→ restore:start → restore:done
→ config:start → config:done
→ cleanup:start → cleanup:done
→ record:done
```

- 回拷阶段透传传输层的 `progress` 事件（已完成字节/文件数、速度、剩余时间）。
- 失败路径在对应阶段发 `failed`，并带 `error_code` / `message`。
- 恢复阶段发 `recover:start` 与 `recover:done|failed`，`failed` 仅对应 `ROLLBACK_RECOVERY_REQUIRED`。

## 10. 本地存储层

### 10.1 数据根布局（§4.2）

```
<data_root>/
  data/<tool_id>/...                 # 迁移后的真实数据
  backup/<stamp>_<tool_id>_<job8>/   # 配置与清单备份
  logs/<yyyy-MM-dd>.log              # 按日 JSONL
  config/
    settings.json
    rules-learned.json
    history.json
    migration-jobs/<job_id>.json
    migration-jobs/<job_id>-rollback.json
    locales/
```

- 默认根：Windows `D:\DiskWarden`，其它平台 `~/DiskWarden`；可用 `DISKWARDEN_DATA_ROOT` 覆盖。
- `DataLayout.ensure()` 只创建目录，不覆盖任何已有文件；`is_writable()` 用带 PID 的探针文件。
- `can_change_root()`：`data/` 非空时拒绝切换数据根（§4.5），同根切换始终允许。

### 10.2 原子写（`atomic.py`）

- `atomic_write_bytes()`：同目录 `*.tmp-<pid>` → 写入 → flush → `os.fsync` → `os.replace`；失败清理临时文件。
- `atomic_write_json()`：UTF-8 无 BOM、`ensure_ascii=False`、`sort_keys=True`、末尾换行；可选保留 `.bak`。
- `read_json_file()` 区分 `FileNotFoundError` 与 `StoreCorruptError`；损坏文件由 `quarantine_corrupt()` 改名为 `*.corrupt-<stamp>`，保留证据。
- `utc_now()` 输出 ISO-8601 UTC、以 `Z` 结尾。

### 10.3 引导指针（`bootstrap.py`）

- 位置在数据根之外：Windows `%LOCALAPPDATA%\DiskWarden\bootstrap.json`；macOS `~/Library/Application Support/DiskWarden/`；Linux `$XDG_CONFIG_HOME/DiskWarden/`；可用 `DISKWARDEN_BOOTSTRAP_PATH` 覆盖。
- `load_bootstrap()` 对缺失/损坏文件返回 `None`，损坏时隔离；`save_bootstrap()` 原子写。
- 启动顺序：bootstrap → 可写数据根 → settings；指针损坏不会让应用忘记数据位置（回退到默认根）。

### 10.4 设置（`settings.py`）

- 已知键：`launch_at_startup`、`data_root`、`language`、`uninstall_policy`、`auto_maintenance`；未知键原样保留（前向兼容）。
- `validate_settings()` 非严格模式返回 `(settings, problems)`，严格模式抛 `StoreError`。
- `SettingsStore.load(repair=False)`：损坏时隔离并回退 `.bak`，再回退默认值；记录 `needs_repair`。`save()` 原子写并保留 `.bak`；`update()` 合并补丁。
- 旧 `schema_version` 会被标记为需要修复；更新的版本号保留，不降级。

### 10.5 历史（`history.py`）

- 单个 `history.json`，含迁移与回滚记录；默认上限 5000 条，超出按时间裁剪。
- `record()` / `record_rollback()` 追加记录；`find()` 支持按 job_id/tool/结果过滤。
- 损坏文件隔离并返回空集合，附 `history_corrupt` warning；单条非法记录跳过并附 warning。

### 10.6 规则学习（`learned.py`）

- 记录每个工具/项的绿/红结论；红表示"迁移后回滚过，需谨慎"。
- `mark_red(item_id, reason, rule_id)` 幂等更新；未知安全值抛 `LearnedRuleError`。
- 兼容裸映射格式；损坏隔离后从空规则集开始。

### 10.7 Journal（`journal.py`）

- 迁移状态：`PLANNED → BACKED_UP → COPYING → COPIED → COPY_VERIFIED → TARGET_READY → SOURCE_RENAMED → LINKED → VERIFIED_LINK → DONE`，另有 `FAILED`、`ROLLED_BACK`、`RECOVERY_REQUIRED`、`LINKED_CLEANUP_PENDING`。
- 回滚状态：`ROLLBACK_PLANNED → LINK_REMOVED → COPYING → COPIED → VERIFIED → SOURCE_READY → CONFIG_RESTORED → ROLLED_BACK`，另有失败/恢复/残留状态。
- API：`begin()`、`load()`、`update()`、`set_intent()`、`set_result()`、`mark_recovered()`、`list_pending()`、`list_all()`、`remove()`。
- 终态集合用于启动扫描：非终态 entry 交给 T10 `recover_job` 或本任务 `recover_rollback`。
- journal 是"意图日志"：每个阶段先写 intent 再执行，崩溃后可用"记录 + 观察"消歧。

### 10.8 日志（`logs.py`）

- 每日一个 `logs/<yyyy-MM-dd>.log`，逐行 JSON、立即 flush；写失败只置 `last_error`，不中断安全操作。
- 字段白名单（`SAFE_FIELDS`），嵌套容器与 bytes 不序列化，避免误记 token 或文件内容。
- `mask_path` / `mask_text` 把用户主目录与已知数据根替换为 `<home>` / `<data_root>`。
- 默认保留 14 天，`rotate()` 只删除匹配日期的旧文件。

## 12. 已知限制与风险

1. **规则置红与 P0 范围存在文档冲突**：`docs/specs/架构设计-v1.0.md` §4.3.4 的 P0 列表未包含"回滚后自动置红"，但 §6.7 与需求 2.4 要求回滚后规则学习置红。本任务按 §6.7 实现；`history_path` / `learned_path` 为可选参数，app 层未接线时不会写文件，因此不影响 P0 验收。
2. **剩余空间检查依赖可注入 provider**：平台层尚无统一的剩余空间原语，当前默认 `shutil.disk_usage`，不可用时只记 warning 并继续。建议后续由平台层补 `free_bytes(path)` 并作为默认注入。
3. **app 层尚未接线**：journal、历史、规则路径均由调用方传入；启动扫描、UI 展示、取消令牌与进度回调属于后续 app 层任务。
4. **`rollback/config.py` 重复声明 `manifest.json` / `files` 常量**：未从 `migrate.backup` 导入，以保持 rollback 包对 migrate 内部结构的低耦合；两边格式变更需同步。
5. **`precheck_rollback` 的迁移 journal 校验是可选强化**：不传 `jobs_dir` 时跳过；app 层应始终传入，避免回滚到与记录不符的路径。
6. **junction 语义仅 Windows**：非 Windows 用目录符号链接；macOS 完整适配由 T21 负责（决策 0004）。
7. **未对真实用户数据演练**：所有测试都在临时沙箱；首次真实回滚建议先在非关键工具上执行并保留备份。
8. **恢复的删除边界**：所有删除都要求路径来自 journal 记录、名称属于本 job、目标带所有权标记；但仍建议 app 层在删除前二次确认用户可见的路径。
9. **残留副本不会自动重试删除**：`residual_copy` 只报告，需用户或后续清理任务显式处理。

## 13. 下一步建议

1. app 层接线：启动时用 `JournalStore.list_pending()` 扫描，迁移 entry 调 T10 `recover_job`，回滚 entry 调 `recover_rollback`，结果进入 UI。
2. 平台层补剩余空间原语，替换 `shutil.disk_usage` 默认实现，并在支持的文件系统上校验同卷判断。
3. 在真实 NTFS 大盘上做一次非用户数据的回滚演练，覆盖十万级文件的回拷/校验耗时与取消响应。
4. 定义残留副本与备份目录的保留策略（按时间、空间与用户确认），接入 `LINKED_CLEANUP_PENDING` / `RESIDUAL_COPY` 的清理入口。
5. 把配置恢复的逐文件结果展示给用户（尤其场景 C），提供"保留我的修改 / 恢复备份"选择。
6. 统一 `rollback/config.py` 与 `migrate/backup.py` 的 manifest 常量，或抽到共享模块，避免格式漂移。
7. 补充端到端测试：迁移 → 回滚 → 重启 → 再次迁移，验证历史、规则与 journal 的连续状态。
