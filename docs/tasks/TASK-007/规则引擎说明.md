## 1. 范围与结论

本任务实现扫描链路的第二层：把扫描条目（工具 + 路径 + 类型）分类为 **green / yellow / red**，并给出规则来源、`rule_id` 与 i18n `reason_key`。不发现目录、不统计大小、不访问文件系统、不做迁移判断。

结论：

- 覆盖目录 `src/core/rules/`，纯标准库实现，Python 3.8 可运行，未新增依赖。
- catalog 由调用方加载后传入，规则层只做纯计算；唯一的 I/O 在 `load_*` 辅助函数里。
- 优先级严格按架构 §4.3：catalog 精确命中 → 本地学习 → 名称/特征规则 → unknown（yellow）。
- red 是终态：catalog red、pattern red、learned red 均不可被绿色规则覆盖；red 永远 `requires_confirm = false` 且 `can_migrate = false`。
- yellow 永远 `requires_confirm = true`，即使 AI 建议绿色也需用户确认，绝不自动进入迁移候选。
- AI 第三层本期仅为接口（T07 不发起任何网络请求），只有 yellow 条目才会咨询 AI。
- `data/rules.json` 现有 27 条规则（15 条 green 精确 + 2 条 green glob + 10 条 red 精确），与 `docs/目录清单.md` §3 规则表逐条一致，本任务未改动数据。
- 单元测试 39 个（规则层专项）全部通过；仓库全量 87 个测试全部通过；`tools/validate_rules.py` 校验通过。

## 3. 优先级与硬约束

### 3.1 分类顺序

1. **catalog 精确命中**：`tool_id` + 规范化路径（含占位符/通配符）命中，来源 `catalog`。
2. **名称/特征规则**：命中即得到 green / red / yellow，来源 `pattern`。red 在此直接返回终态。
3. **本地学习**：同一 `item_id` 的学习记录，来源 `learned`。只能把 green 降为 red、把 yellow 升为 green 或 red；不能软化 red，也不能把 green 直接变回 yellow。
4. **兜底**：yellow + unknown，`requires_confirm = true`。
5. **AI 接口（本期不启用）**：仅当当前结论为 yellow 且调用方注入了 `ai_resolver` 时才咨询；返回 green/red 时来源 `ai`，且强制 `requires_confirm = true`。

> 说明：catalog 条目本身已含安全级别，因此 catalog 命中后不再走 pattern；学习记录对 catalog 命中同样生效（用户决定优先于静态规则），但 red 不可被软化。

### 3.2 硬约束（均有测试）

- red 不可被任何 pattern/learned/AI 结果覆盖；`requires_confirm = false`，`can_migrate = false`。
- yellow 永远 `requires_confirm = true`；`can_migrate` 仅在 `safety == green` 且无需确认时为 true。
- AI 建议绿色仍 `requires_confirm = true`，不会自动迁移。
- 规则层的 `reason` 为英文兜底文案，界面展示应使用 `reason_key`（架构 §4.3）。
- 未知目录默认 yellow，绝不判为可迁移。

## 4. 匹配语义

### 4.1 名称规则

- 只匹配 **basename**（目录/文件名），不匹配整条路径。
- 大小写不敏感（Windows 语义）；`\` 与 `/` 均作为分隔符。
- 末尾的空格与点被忽略（Windows 文件系统语义）；**内部空格有意义**，`Code Cache` 与 `CodeCache` 是不同名称。
- `match_type` 支持：
  - `exact`：规范化后完全相等；
  - `glob`：`fnmatch` 语义，必须含 `*`；
  - `regex`：`re.IGNORECASE` 下 `fullmatch`。
- 多条规则同时命中时 **red 优先**（`conflict_resolution = "red_wins"`），其次 green，再 yellow；`rules.json` 的加载器会拒绝重复的 `(match_type, match)`。

### 4.2 catalog 匹配

- 占位符 `%APPDATA%` / `%LOCALAPPDATA%` / `%USERPROFILE%` 从调用方注入的 `environ` 展开，变量名大小写不敏感；未解析的条目被跳过并产出 `RuleWarning(code="unresolved_environment")`，不中断加载。
- 路径分段规范化：`/` 与 `\` 等价、忽略空段、忽略段尾空格与点、大小写不敏感。
- `<...>` 占位段匹配 **恰好一个非空段**（如 Claude Code 的 `<项目>`）。
- `glob` 条目只在最后一段支持 `*` / `?`（如 `*.log`、`*.sqlite`）。
- `kind` 必须一致（`dir` / `file`）。
- 多个条目同时命中时按具体度排序：字面量段多者优先 → 段数多者优先 → 非 glob 优先 → 模板长者优先 → red 打破平局。

## 5. 公开 API

```python
from core.rules import ClassifyEngine, RuleItem, load_engine

engine = load_engine(
    "data/rules.json",
    "data/ide-catalog.json",
    environ=os.environ,
    learned=[],          # 可选：LearnedRule 列表或 [{"item_id": ..., "safety": "red"}]
    ai_resolver=None,    # 可选：本期不要注入真实网络实现
)

result = engine.classify(RuleItem(tool_id="vscode", source_path=r"C:\Users\me\AppData\Roaming\Code\Cache"))
result.safety            # "green"
result.source            # "catalog" | "learned" | "pattern" | "unknown" | "ai"
result.reason_key        # i18n key
result.requires_confirm  # bool
result.can_migrate       # 仅 green 且无需确认时为 True
result.to_dict()         # 便于跨层/日志序列化
```

- `ClassifyEngine.classify_name(name)`：只按名称规则分类，便于 UI 预览与测试。
- `ClassifyEngine.classify_many(items)`：保持输入顺序，返回 `Classification` 列表。
- 输入既可以是 `RuleItem`，也可以是具备 `tool_id` / `source_path` / `kind` 等字段的对象或 dict；`item_id` 可由调用方显式传入，否则按 `sha256(tool_id + "\n" + 规范化路径)[:16]` 生成，大小写不敏感。
- `load_name_rules` / `load_catalog` / `parse_name_rules` / `parse_catalog`：严格校验，错误聚合为 `RulesError`（含 `errors` 列表）；catalog 的环境变量缺失属于警告而非错误。

## 7. 风险与待确认

1. **catalog 准确性（R8）**：分类上限取决于 `ide-catalog.json` 的覆盖面；未收录的新版本目录会落到名称规则或 yellow。需要 T03 持续维护，且产品侧接受"未知即 yellow"。
2. **`<...>` 占位段较宽松**：匹配任意单段，可能把项目内的同名子目录误判到该工具规则下；当前依赖路径前缀（projects 等）收窄范围，后续可按真实样本收紧。
3. **`item_id` 稳定性**：基于工具 + 规范化路径计算。用户移动数据目录或环境变量变化会生成新 id，历史学习记录不会自动跟随；T11 持久化时需要接受这一语义。
4. **AI 层本期离线**：仅保留 `AIResolver` 接口，不会发起网络请求；接入前需先经过安全评审（决策 0001/0002/0003，风险 R6）。
5. **学习数据归属**：规则层只消费学习记录，不负责写入与 7 天无回滚判定；该逻辑在 app/history（架构 §4.3 明确放在规则层之外）。
