# T12-F 回滚：配置恢复误报 "backup manifest is missing"

## 现象

真机回滚任务 `41f1cf8f6bd3447bb1adf16a8dd86e05`
（`C:\Users\Administrator\.vscode\extensions` → `D:\DiskWarden\data\vscode\extensions`）：
数据回滚成功（`ROLLED_BACK`、`target_removed=True`、`residual_copy=False`、
源目录完好、`extensions.json` 的 sha256 与清单一致），但配置步骤返回：

```
result.config.status   = unavailable
result.config.ok       = False
result.config.reason   = backup manifest is missing
```

而 `D:\DiskWarden\backup\2026-10-20_161403_vscode_41f1cf8f\manifest.json`
实际存在，`job_id` 与本次迁移一致，清单中有 1 条 `extensions.json`。

## 根因

两处缺陷叠加：

1. **迁移日志记录的是备份根目录，而不是本次任务的备份目录。**
   `src/app/service.py` 在打开迁移日志时写入 `backup_dir=self.layout.backup_dir`
   （如 `D:\DiskWarden\backup`），而 `prepare_copy` 完成后才在
   `prepared.backup_dir` 给出真正的
   `D:\DiskWarden\backup\2026-10-20_161403_vscode_41f1cf8f`。
   回滚、崩溃恢复都直接读日志里的 `backup_dir`。
2. **配置恢复把该路径当作"备份目录"直接拼 `manifest.json`。**
   `restore_configs` 只在 `<backup_dir>/manifest.json` 查找，找不到就报
   "backup manifest is missing"，没有按任务 `job_id` 去备份根下定位。

时间戳只是备份目录名的一部分（迁移时间 16:14:03），代码并未用回滚时间去拼路径；
真正的问题是"路径式查找"而不是"按 job_id 查找"。因此即便日志里是根目录，
也不应把它当成配置缺失。

## 修复

### 1. 按迁移 job_id 定位清单（`src/core/rollback/config.py`）

- 新增 `locate_manifest(backup_dir, expected_job_id, expected_tool_id)`：
  - 传入的路径既可以是本次任务的备份目录，也可以是备份根目录，甚至可以是
    `manifest.json` 文件本身；
  - 若传的是根目录，扫描其子目录，按清单里的 `job_id` 匹配（同时校验
    `tool_id`）；目录名里的 `<job8>` 后缀只作为旧清单缺少 `job_id` 时的兜底，
    从不根据时间戳拼路径；
  - 多个候选时优先目录名后缀匹配的任务目录，其余按名称稳定排序，错误信息
    汇总所有不匹配原因。
- `restore_configs` 改为先定位清单，再执行 A/B/C/D 恢复；对外区分三种状态。

### 2. 三种状态，不再一律报 missing（`src/core/rollback/models.py`）

| status | 含义 | `ok` |
| --- | --- | --- |
| `skipped` | 迁移没有改动配置：无备份记录、清单为空、或所有文件与备份一致/按策略保留 | `True` |
| `restored` | 至少写入了一个文件，且清单内每个条目都有结论；逐文件返回 sha256 | `True` |
| `error` | 清单缺失/损坏/属于其他任务，或某个文件无法校验、写入失败；`reason` 指明文件 | `False` |

- 结果对象新增 `backup_dir`、`manifest_path`、`checksums`，每个条目的
  `details` 带 `sha256` / `expected_sha256` / `verified` / `reason`。
- 写入后用备份内容重新哈希（`written_digest`），不一致记为
  `restore_failed`，避免"写成功但内容不对"。
- 空备份记录（迁移没动配置）返回 `skipped` +「没有任何配置文件需要恢复」，
  不再作为失败。

### 3. 数据结论与配置结论分开呈现

`RollbackResult` 增加 `data_rolled_back` 与 `config_status`，`to_dict()` 同时输出。
`RollbackResult.ok` 仍然只代表数据回滚结果；配置 `error` 只追加 warning，
不会改写数据结果，也不会删除任何已存在文件。

### 4. 迁移日志记录任务级备份目录（`src/app/service.py`）

`prepare_copy` 成功后把 `prepared.backup_dir` 写回迁移日志
（`journals.update(job_item_id, backup_dir=prepared.backup_dir)`）。
新任务从源头记录正确路径；旧日志（记录根目录）由第 1 点的扫描逻辑兼容。

## 安全性

未改动迁移/回滚的安全语义：

- 配置恢复仍然只写清单内的文件，路径经过 `_safe_rel_path` + `is_inside` 校验；
- 失败不清除用户现有文件，写入走 `atomic_write_bytes`；
- 失败时源目录保持逐字节不变（闭环演练中 `source_intact=True`）。

## 测试

新增/重写 `tests/test_rollback_config.py`（27 条）覆盖：

- 清单在带时间戳的任务子目录、只传备份根（本 issue 场景）；
- 任务目录被改名后仍按清单 `job_id` 匹配；
- 备份根下多个任务目录时选中 `job_id` 匹配的那个；
- 清单确实缺失、备份目录不存在、清单损坏、清单属于其他任务/工具；

- 逐文件 sha256、写入后校验、部分失败时 `error` 指明文件、写失败保留原文件；
- 不安全相对路径、非对象条目、缺少 `source_root`、`entries` 非列表。

- 日志记录备份根时配置仍为 `restored` 并返回 sha256；
- 未记录任何备份时配置为 `skipped`，数据结果仍为 `ROLLED_BACK`。

结果：`python -m unittest discover -s tests -q`，**594 条全部通过**。

## 临时数据根闭环演练

使用临时目录完成真实 `prepare_copy → complete_migration → rollback`，
迁移日志故意写入备份根目录（复现旧版本行为），配置恢复结果为：

| 场景 | state | config.status | 校验 |
| --- | --- | --- | --- |
| 配置未被改动 | `ROLLED_BACK` | `skipped` | 当前文件 sha256 与清单一致 |
| 配置被用户修改 + `CONFIG_RESTORE` | `ROLLED_BACK` | `restored` | `checksums["extensions.json"]` 与清单一致 |

两种场景均为 `target_removed=True`、`source_restored=True`、
`source_intact=True`，未再出现 `unavailable` / `missing`。

- 旧版本写下的迁移日志（`backup_dir` 为根目录）可直接回滚，配置状态正确；
- 配置恢复的 `keep` 默认策略不变；
- 状态枚举由 `unavailable/not_required/kept/partial/restored/failed` 收敛为
  `skipped/restored/error`，仓库内无其他消费方（UI 未读取该字段）。
