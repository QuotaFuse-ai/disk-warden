# Disk Warden 协作规范

> 版本：v1.0
> 日期：2026-10-19
> 负责人：运维工程师
> 适用范围：`D:\workplace\disk-warden` 本地仓库（当前无远端）

## 一、仓库状态与基本约束

- 仓库**仅存在于本地**，未配置任何 remote。未经人类确认，不得添加远端、推送或发布。
- 主线分支为 `main`，初始提交包含需求文档、目录清单、调研、静态原型与协作基建。
- 本仓库是多 agent 共用的同一个工作区，**禁止在共享工作区随意切换分支**（会直接影响他人正在编辑的文件）。分支规则见第四节。
- 不删除任何现有文件；需要清理的临时脚本保持在工作区，通过 `.gitignore` 排除即可。
- 仓库级提交身份目前为占位值 `Disk Warden Team <dev@disk-warden.local>`（机器上没有配置全局 Git 身份）。如需以个人名义提交，使用 `git config --local user.name/user.email` 覆盖，不要改动全局配置。

## 三、文档规则

1. **`docs/multica-handover/` 只读**：接手报告一经生成不允许覆盖或编辑。发现内容过时可以新增一份带日期的补充报告，不得改动原文件。
2. **`docs/decisions/` 只增不改**：每个决策一个文件，命名 `000N-主题.md`。禁止修改或删除既有决策；推翻旧决策时新建一条，并在正文注明「取代 000N」。
3. **`docs/tasks/TASK-XXX/` 按任务隔离**：只写自己任务目录，产出用 Markdown，文件名能独立表意。不得把其他任务的产出挪进来。
4. **`docs/specs/` 只保留最新版本**：规格更新时在文末维护「变更记录」（日期、变更人、变更点），不保留过期副本。
5. **强制引用**：开始新任务前先读 `docs/multica-handover/`（如存在）与相关 `docs/specs/`，避免基于过期结论施工。
6. 文档统一使用 UTF-8 编码、Markdown 格式、中文正文；一个文件只用一个一级标题。

## 四、分支与提交

### 4.1 分支策略

- 阶段 1（定义与地基，纯文档/基建）：直接在 `main` 上提交，保持历史线性。
- 阶段 2 起（代码实现）：实现类改动必须使用独立分支，且**不得在共享工作区切分支**。做法是从本目录复制/使用独立检出目录，或由执行业务的子任务使用独立 worktree。
- 分支命名：

| 类型 | 格式 | 示例 |
|---|---|---|
| 功能 | `feature/<issue>-<短描述>` | `feature/quot-6-scan-core` |
| 修复 | `fix/<issue>-<短描述>` | `fix/quot-9-robocopy-exitcode` |
| 文档 | `docs/<短描述>` | `docs/collaboration-rules` |
| 基建/杂务 | `chore/<短描述>` | `chore/git-init` |

- 分支从最新 `main` 切出；合并前先同步 `main`，本地合并即可（暂无远端）。

### 4.2 提交信息

采用 Conventional Commits，描述用中文：

```
<type>(<scope>): <一句话说明>

<可选正文：为什么改、影响范围>
(QUOT-7)
```

- `type`：`feat` / `fix` / `docs` / `chore` / `test` / `refactor`
- `scope`：`scan` / `rules` / `migrate` / `rollback` / `store` / `ui` / `docs` / `dev`
- 一次提交只做一件事；产物与源码分开提交。
- 已合并进 `main` 的提交不得 amend 或 rebase 重写；不使用 `git push --force`（未来有远端时同样适用）。

## 五、禁止提交清单（强制）

以下内容**任何情况下都不得进入版本库**，`.gitignore` 已做兜底，但提交前仍需人工确认。

### 5.1 凭据类临时脚本

| 文件 | 原因 |
|---|---|
| `check*.py`（`check.py`、`check2.py` … `check10.py`） | 内含服务器 root 明文密码，SSH 探测脚本 |
| `upload*.py`（`upload.py`、`upload2.py`、`upload_login.py`） | 同上，SFTP 上传脚本 |
| `test_ssh.py` | 同上，SSH 连通性测试 |
| `clean.py` | 同上，远程删除文件脚本 |

这些文件只保留在本机工作区，禁止改名、复制或摘录其中的连接信息。

### 5.2 其他禁止项

- 任何密钥、证书、SSH 私钥、云厂商凭据：`.env*`、`*.pem`、`*.key`、`id_rsa*`、`.credentials.*` 等
- 本地配置：`*local.json`、`settings.local.json`、`config.local.*`、`.vscode/`、`.idea/`
- 真实用户数据：`%APPDATA%` / `%USERPROFILE%` 的采样目录、会话数据库、备份目录
- 截图类临时脚本与截图：`shot*.py`、`screenshot.py`、`ui*.png`、`**/_shots/`
- 生成物：`dist/`、`build/`、`__pycache__/`、`node_modules/`、`*.log`、`*.spec`
- 大文件：超过 10 MB 的二进制、安装包、压缩包（`*.exe`、`*.msi`、`*.dmg`、`*.iso`、`*.zip` 等）

### 5.3 发现泄露时

1. **立即停止提交**，不要把内容贴进 issue 或评论。
2. 在 issue 中说明文件名与风险等级（不要贴凭据本身），@ 人类处置。
3. 已进入历史的凭据按风险 R2 处理：由人类轮换密码、改用 SSH key；**开发人员不得自行修改服务器或轮换凭据**。
4. 需要清理历史时，由人类确认后再决定是否重建仓库。

## 六、提交前检查

每次 `git add` 后、`git commit` 前执行：

```bash
git status --short                 # 确认只有预期文件
git diff --cached --stat           # 确认没有大文件
git diff --cached | grep -inE "password|passwd|secret|api[_-]?key|BEGIN .*PRIVATE KEY"
```

最后一条应无输出；有输出则立即 `git reset` 并排查。

个人临时忽略项写入 `.git/info/exclude`，不要修改 `.gitignore`（避免影响全队）。`.gitignore` 的调整由运维工程师在对应 issue 中处理。
