# 2026-10-20 · 阻塞重检复用 `scan.result`，不新增 RPC

## 背景

v0.2 §10 要求在迁移阻塞弹窗内提供「重新检测」，检测完成后在同一弹窗内就地切换为「仍阻塞 / 已解除 / 检测失败」。现有 RPC 共 26 个方法，没有进程重查或阻塞复检接口。

## 决策

点击「重新检测」时调用既有 `scan.result`，用返回快照重建 `CATALOG`（`setSnapshot`），再从 `runtime.running` 重新取进程列表，与检测前的 `name#pid` 集合比较：

- 新集合为空 → 已解除；
- 有交集 → 仍阻塞，消失行淡出、保留行闪烁；
- RPC reject → 检测失败，保留原列表。

8 秒未返回视为超时，丢弃迟到结果。

## 理由

- 不扩大后端接口面，符合「所有交互必须能落到现有 RPC」的约束。
- `scan.result` 已包含 `runtime.running`，足以判定阻塞是否解除。
- 同一弹窗内维护 `state.blockedRecheck` 状态机，避免重开弹窗丢失滚动位置。

## 代价

- 检测是一次全量快照刷新，比单点进程查询重；当前规模可接受。
- 若后端后续提供轻量重检接口，只需替换 `App.recheckProcess()` 内的 `rpc('scan.result')` 调用，状态机与 UI 不变。
