# 决策 0003：运行时外壳最终选型（提议 Python + pywebview，待人类确认）

- 日期：2026-10-19
- 决策人：后端架构师（提议）
- 状态：**待人类确认**（确认后由项目领导人追加确认记录；本文件只增不改）
- 关联：`docs/decisions/0002-运行时外壳选型待确认.md`、`docs/specs/架构设计-v1.0.md`
- 任务：QUOT-4 / T02

## 1. 背景

`docs/decisions/0002` 登记了运行时外壳的冲突：需求文档写 Python 3.12 + HTML + PyInstaller，团队背景写 React + Electron，仓库里的 `main.py` 是 Tkinter 空壳。阶段 2 的实现类任务依赖该结论，必须先拍板。

本决策在 T02 中完成量化对比后给出**明确推荐**，不采用"各有优劣"的折中结论。完整对比、五层架构、UI 协议与迁移安全设计见 `docs/specs/架构设计-v1.0.md`。

## 2. 决策

**采用方案 A：Python 3.12 + pywebview（系统 WebView2）+ PyInstaller（onedir）+ Inno Setup。**

具体含义：

1. **宿主进程**用 Python 3.12 实现，负责扫描、规则、迁移、回滚、存储与窗口生命周期。
2. **界面**用 WebView2 承载本地静态资源；P0 直接使用现有 `ui/index.html`（原生 JS），P1 可独立引入 Vite + React 构建成静态资源，不改变宿主选型。
3. **打包**采用 PyInstaller onedir（不用 onefile）生成免安装目录，再由 Inno Setup 封装安装器；属于 P1/T15 范围。
4. **平台适配层**隔离全部 Windows 调用（junction、卷信息、进程、robocopy、长路径），Mac 后续替换该层即可。

## 3. 量化依据

数据口径见架构设计 §2.1；体积/内存/启动为工程估算，需在 T15 前的 spike 中实测校准。

| 维度 | A：Python + pywebview + PyInstaller | B：Electron + React |
|---|---|---|
| 安装包体积 | **25~40 MB** | 90~130 MB |
| 安装后磁盘 | **70~110 MB** | 250~350 MB |
| 冷启动（SSD） | **0.6~1.2 s**（onedir） | 1.5~3.0 s |
| 常驻内存 | **90~160 MB** | 220~400 MB |
| 进程枚举耗时 | **50~200 ms**（psutil） | 400~1200 ms（PowerShell CIM）或原生模块 |
| junction 删除安全性 | **已实测**：`os.rmdir` 只删链接、目标完好；`st_reparse_tag` 可识别 | 需自行证明 libuv 递归删除语义并做破坏性测试 |
| 系统能力开发 | 标准库直连 | 需桥接或 sidecar |
| UI 开发 | 与 B 相当（可加载同一套静态/React 产物） | 与 A 相当 |
| 跨平台（Mac，P2） | 3~5 人日适配 | 2~4 人日适配 |
| 团队匹配 | 系统层匹配 Python；UI 仍可用 React | 名义匹配，但背景被判定为模板 |
| 故障可控性 | 单进程、步骤边界清晰 | 多进程 + IPC + 原生模块，面更大 |

补充实测（本机，Python 3.8.6 / Windows 10）：裸解释器启动 Python 36 ms、Node 30 ms，语言运行时本身不是差异来源；真正的差异来自浏览器引擎（系统 WebView2 vs 自带 Chromium）。

## 4. 理由

1. **产品是系统操作密集型，不是界面密集型。** 核心是扫描、校验、搬运、junction、回滚；UI 只有 5 个 Tab 与少量弹窗，用自带 Chromium 的成本与收益不匹配。
2. **破坏性操作要求可控的系统语义。** Python 标准库可直接判定 reparse point 与重解析标签，删除链接的行为已在本机验证；Node 侧需要额外证明递归删除语义。对一个会删用户数据的工具，这个差异是决定性的。
3. **体积与冷启动是用户可感知的。** 安装包约为 B 的 1/3，冷启动约快 1 倍。
4. **React 与 Electron 解耦。** 前端可用 Vite + React 构建为静态资源，由 pywebview 加载；选择 A 不会损失前端工程化能力。B 的唯一强项（自动更新生态）在本期 P2 之外。
5. **与现有文档和模块划分一致。** 需求文档第 4 章、决策 0001 的 `src/*` 划分均按 Python 编写；选 A 不产生文档返工。
6. **风险最小。** 不引入 Node 原生模块，不维护宿主 + sidecar 双运行时，不需要 Electron 安全加固（`contextIsolation`/`sandbox`/IPC 白名单）也能保持较小的攻击面。

**否决 B 的结论**：B 的跨平台一致性与复杂前端生态优势不构成本项目的关键路径；在本产品的风险结构下，B 增加的是封装层与安全面，而不是产品价值。

**若人类改选 B**：业务层可作为 Python sidecar 保留，五层边界、迁移状态机与 UI 协议原样复用，仅替换宿主桥与平台适配实现；但需接受安装包增加约 25 MB 运行时与 sidecar 生命周期管理成本，不推荐。

## 5. 影响

### 5.1 与决策 0001 的关系

**不冲突。**

- 0001 的 P0 主链路（扫描 → 规则 → 迁移 → 备份 → 校验 → junction → 验证 → 回滚）、P0/P1/P2 范围、降级原则全部保持不变。
- 0001 列出的 `src/scan`、`src/rules`、`src/migrate`、`src/rollback`、`src/store` 五个模块全部保留，在架构设计中归入 `src/core/`，分别对应五层中的扫描层、规则层（迁移层包含 migrate + rollback）、存储层。
- 本决策新增 `src/app`（宿主桥/生命周期）与 `src/platform`（Windows 适配）两个**非业务目录**，以及 `src/ui` 静态资源目录；不新增产品功能，不改变 P0 范围。
- 0001 中打包/托盘/OAuth 属于 P1 的结论不变：本决策只锁定技术路线，不提前实施 T15。

## 6. 待人类确认

以下问题超出架构师权限，需要人类拍板。**在第 1 项确认前，阶段 2 实现类任务仍不启动。**

1. **是否采用方案 A（Python 3.12 + pywebview + PyInstaller）？** 若无特别偏好，建议采用 A。
2. **产品范围**：本期是否仅为"disk-warden 单机工具 + 官网"？还是要做"官网 + 主机端 hub + 个人端 dsk"三端？现有需求文档只支持前者；若要做三端，需另立决策与预算。
3. **Python 3.12 构建环境**：当前开发机只有 Python 3.8.6。是否同意在开发机/CI 安装并使用 3.12 构建？（最终用户不需要安装 Python；打包后的程序自带运行时。设计已保留 3.8 可用的 reparse tag 判定作为兜底，但基线仍要求 3.12。）
4. **WebView2 依赖**：是否接受依赖系统 WebView2（Win11 与已更新 Win10 通常自带；极老系统需安装）？若不接受，只能改回 B 或接受更大的安装包。
5. **重命名换位方案**：迁移的关键步骤采用"源目录原子重命名为 tombstone → 建 junction → 验证后异步清理 tombstone"，而不是"直接递归删除源目录"。这会短暂占用双份空间且成功后仍有删除动作，但数据安全性显著更高。是否认可？
6. **bootstrap 指针**：为支持用户自定义数据根目录且防止可移动磁盘掉线导致配置丢失，计划在 `%LOCALAPPDATA%\DiskWarden\bootstrap.json` 增加一个指向 data_root 的小文件（需求文档 4.2 未包含）。是否接受这一补充？
7. **规则学习"自动绿色"的观察期**：需求 2.4 写"迁完没回滚=安全"。建议同一目成功迁移且 **7 天内未回滚**才自动加入绿色列表；是否认可该时长？（P0 不依赖此策略，可先人工标记。）
8. **代码签名（P1）**：是否愿意承担代码签名证书成本以降低 SmartScreen 拦截？不签也可发布，但首启体验会受影响。

> 第三层"AI 分析未知目录"是否联网、是否接受模型费用，0002 已列为待确认项（风险 R6）；本期按决策 0001 不实现，仅保留接口。若范围扩展到三端，本条需一并重新确认。

**确认方式**：人类在本 issue（QUOT-4）或 QUOT-2 下回复"采用 A"及上述各项意见；由项目领导人将确认结果追加到本文件末尾（不修改上述历史内容），并同步更新阶段 2 的任务状态。
